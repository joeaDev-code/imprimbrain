# Backend Security Consolidation

## Tenant Isolation

The current API derives `organizationId` from the authenticated session. The review of all 17 API route handlers found no reachable cross-organization read or write. Create handlers use the session organization; direct entity lookups include it; nested order/payment and service/stock relations are validated against it. Mutations now retain the tenant predicate in their final write wherever Prisma supports it. `ConsumptionRule` creation checks both related rows, and its reads check both sides.

The Prisma schema and initial migration do not define PostgreSQL RLS. This is a defense-in-depth gap, not a currently demonstrated API bypass. Relations such as `OrderLine -> Order`, `Payment -> Order`, `ConsumptionRule -> Service/StockItem`, and `StockMovement -> StockItem/Order` use individual foreign keys; the database does not itself prove that both related records belong to the same organization.

A safe RLS rollout must not consist of enabling policies alone. Current code performs direct Prisma queries as well as interactive transactions; setting an organization variable on a pooled connection would risk leaking tenant context to another request. The compatible design is:

1. Introduce a request-scoped `withTenantTransaction(organizationId, callback)` wrapper that starts a Prisma transaction and executes `SELECT set_config('app.current_organization_id', $1, true)` before tenant queries. The `true` flag makes the setting transaction-local.
2. Move every tenant-owned read and write into that wrapper, including nested queries and the existing payment/order/stock transactions. Authentication bootstrap (`Session` and the initial `User` lookup) needs separate policies that bind rows to the authenticated user, not an unset organization variable.
3. Add policies with both `USING` and `WITH CHECK` for tables carrying `organizationId`; add relation-aware policies for child tables without that column. Add same-tenant relation constraints or equivalent validation for indirect relationships.
4. Apply policies only after integration tests prove that missing context returns no tenant rows, mismatched relations are rejected, and requests under two organizations cannot see or mutate each other's records. Use a non-owner runtime DB role without `BYPASSRLS`, then consider `FORCE ROW LEVEL SECURITY`.
5. Deploy as an additive migration with a rollback plan after backups and staging verification. No RLS migration was created or applied during this consolidation, and Neon was not modified.

## Login Rate Limiting

`RateLimitStore` is the application boundary; `MemoryRateLimitStore` is bounded and intended for one process only. The login route counts failures, hashes account/IP keys, and applies a short progressive account delay rather than a 15-minute account lock. `TRUSTED_PROXY_IP_HEADER` accepts only `x-real-ip` or `x-forwarded-for`; configure it only where the edge proxy overwrites the selected header. With no trusted proxy configured, IP limiting is intentionally disabled rather than based on attacker-controlled headers.

Before multi-instance/serverless deployment, provide an atomic distributed adapter for `RateLimitStore` or enforce equivalent limits at the trusted edge. The in-memory implementation cannot coordinate workers, regions, or cold starts.

## Public Receipts

The current new-order workflow displays an authenticated, organization-scoped receipt modal through `GET /api/receipts/:id`; this explains why `createPublicReceiptToken()` has no issuance call site. No public receipt link is generated by the current application flow.

The separate legacy `/recu/:token` route remains available for an explicitly issued bearer token. Tokens use HMAC-SHA-256 and expire after 30 days. Possession grants read access to the receipt for that period; the page exposes organization contact information and order/payment details, but not client phone, WhatsApp, or email. It uses `no-store`, `no-referrer`, and `noindex` headers. There is no per-token revocation record; rotating `PUBLIC_RECEIPT_SECRET` revokes all such tokens. Do not add a public issuance button without a product decision on sharing, revocation, and which receipt fields are appropriate to disclose.
